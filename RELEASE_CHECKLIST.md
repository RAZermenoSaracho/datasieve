- [x] Installation verified — all 4 tarballs installed together via plain `npm install` in a temporary project outside this workspace (no workspace linking); CJS `require()`, ESM `import`, and TypeScript compilation (including `@ts-expect-error` cases proving the type system is real, not `any`) all verified against the installed packages; a full Prisma-backed query executed end to end against a real SQLite database using only the published-shape tarballs.

**Blocking action before first publish:** the `@datasieve` npm scope does not appear to be registered yet (`npm view @datasieve/core` returns 404, which is expected pre-publish but also means the org/scope itself may not exist under the publishing account). Create it on npmjs.com (or confirm it already exists under your account) before running `pnpm publish` on any `@datasieve/*` package — a `publishConfig.access: public` package fails to publish under an unregistered scope.

## Post Release

- [ ] GitHub Release — create one at `https://github.com/RAZermenoSaracho/datasieve/releases/new`, tag `v0.1.0`, body from `RELEASE_NOTES_0.1.0.md`.
- [ ] CHANGELOG — this project doesn't have automated changelog tooling yet (Changesets is still listed as open in `CLAUDE.md`'s Phase 1); for this first release, `RELEASE_NOTES_0.1.0.md` doubles as the changelog. A `CHANGELOG.md` per package is worth adding before v0.2.0 once there's a second release to diff against.
- [ ] Git tag — `git tag v0.1.0 && git push origin v0.1.0` (only after publishing succeeds — tagging before a failed publish leaves a tag pointing at unreleased code).

## Exact publish order

```sh
cd packages/query-language && pnpm publish
cd ../core && pnpm publish
cd ../prisma && pnpm publish
cd ../datasieve && pnpm publish
```

Each step must succeed on the registry before the next begins — every later package's `workspace:*` dependency needs the earlier one to actually exist at the version being rewritten to.
